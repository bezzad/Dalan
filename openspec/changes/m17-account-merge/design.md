# Design

- **Proof before reveal.** The server says a phone, email or GitHub account belongs to another account only after the proof (right SMS code, right email code, GitHub callback). So a logged-in user cannot test numbers to find accounts.
- **Pending merge.** After the proof the server stores one pending merge per session in `identity.pending_merges` (`session_id` unique, `user_id`, `other_user_id`, `way`, `expires_at`; expiry `Identity:MergeSeconds`, start 600). The client never holds a merge secret: `GET /api/account/merge` shows it, `POST /api/account/merge` does it, `DELETE /api/account/merge` drops it. A new proof replaces it.
- **Products.** Not deleted bots (Relay), sites and demos (Sites), access keys (Identity). Identity asks Relay and Sites through their `.Contracts` (`IUserHoldings.CountAsync(userId)`), right before the merge.
- **GitHub link.** The session cookie is `SameSite=Strict`, so the way back from github.com does not carry it. `GET /api/account/github` stores `identity.github_links (state_hash, session_id, expires_at)`; the callback finds the link by the hash of its state and links instead of logging in.
- **The merge transaction (Identity).** One transaction: lock both user rows, check the pending merge and the fields again, delete the other user first (its phone, email, GitHub id and username are unique; sessions, keys and pending merges go by cascade), move the empty fields to the kept user, and write `identity.merges (from_user_id, into_user_id, way, merged_at, done_at)`. The audit row is written after the commit. A bot made by the other account in the moment between the product check and the transaction is not lost: Relay moves its owner too (there should be none).
- **Follow-up (the outbox).** Every `IUserMergeListener` (Identity.Contracts) runs right after the commit; `identity.merges.done_at` is set when all are done. `MergeFollowUp` tries the rest again every `Identity:MergeRetrySeconds` (start 60). Relay is the listener; it moves push subscriptions through `IWebPush.MoveAsync`. Holdings come from every `IUserHoldings` (Relay: bots and chats; Sites: sites and live demos).
- **Chats (Relay, on `UserMerged`).** Per bot:
  - Only the gone user has a chat: change `user_id` on the membership, its messages and files. Ids stay.
  - Both have a chat: order both message lists by `date`, then the kept user first, then old id. New ids start after the largest old id of both chats (`max + 1`, `max + 2`, ...), versions the same way. So an old message id never points to another message: a bot that edits or replies to an old id gets "message not found". Read position: the new id of the last read message of the kept chat. The gone membership is deleted. A live `reset` event makes the kept user's clients load the page again.
  - In both cases `relay.moved_chats (bot_id, from_user_id, to_user_id, at)` gets a row, and the bot queue gets one `chat_moved` update.
  - `moved_chats` rows live `Relay:MovedChatDays` (start 180); after that a send to the old id gets `chat_not_active`.
- **Push subscriptions (Notification, on `UserMerged`).** Move to the kept user; beyond `MaxSubscriptionsPerUser` the oldest go.
- **Logs.** `admin.access_log` rows are never changed (rule 13): the gone id stays in old rows. The audit row is `user {from} merged into user {into}` with the way.
- **Bot API names.** The Bot API calls a chat by `user_id`, so the update is `chat_moved: {from_user_id, to_user_id, date}` and the error carries `to_user_id`. The `chat_moved` update lives in the in-memory queue like any update (Q-02); a bot that was offline still gets the error with the new id.
- **New settings:** `Identity:MergeSeconds` = 600, `Identity:MergeRetrySeconds` = 60, `Relay:MovedChatDays` = 180.
